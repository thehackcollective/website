# Cloudflare: the `cf` CLI and the Vite plugin 2.0 beta, not Wrangler

Status: accepted
Date: 2026-11-12
Scope: both Workers (the site and Work), local D1, the gate and the Workers Builds deploy.
Decision:
1. The repo uses `cf` 1.0.0-beta.28 and `@cloudflare/vite-plugin` 2.0.0-beta.v.12, pinned exactly, as in cf0.ai, senvielab and elearning. Wrangler is not a dependency. Scripts call `node_modules/.bin/cf`, never a global `cf` and never `wrangler`.
2. Each Worker is one `cf` project: a directory with `cloudflare.config.ts` and `vite.config.ts`. The plugin reads the config from the Vite root, and `cf` reads the config in the directory it runs in.
   - The site is the repo root. `cloudflare.config.ts` declares an assets-only Worker named `website` with no entrypoint, the `hackcollective.uk` and `www.hackcollective.uk` domains, and single-page-application not-found handling.
   - Work is `internal/`, which is already Work's Vite root with `index.html`. `internal/cloudflare.config.ts` declares `hack-collective-work` with `entrypoint: '../workers/internal/index.ts'`, the `app.hackcollective.uk` domain, the `ASSETS` binding and the `DB` D1 binding.
3. A build writes `.cloudflare/output/v0/` next to its config. Git ignores `.cloudflare/`, and ESLint skips it. `bun run build` builds the site. `cd internal && bunx vite build` builds Work.
4. D1 migrations stay in `workers/internal/migrations` and keep Wrangler's `d1_migrations` table, so production does not apply them again. `cf` has no migrations-dir key, so every command passes `--dir`. `cf` defaults to the remote database, so local commands pass `--local --persist-to <dir>`. `./c check schema` applies the migrations to a fresh directory and expects `cf d1 migrations list` to return `[]`.
5. Workers Builds deploys each Worker with `cf deploy --prebuilt --mode production`:
   - site: build `bun install && bun run build`, deploy `bunx cf deploy --prebuilt --mode production`.
   - Work: build `bun install && cd internal && bunx vite build`, deploy `cd internal && bunx cf deploy --prebuilt --mode production`.
   - Both exclude `**/.cloudflare/**` from the watch paths. The triggers change right before the merge that ships this record, because the old commands fail on the new tree and the new commands fail on the old tree.
6. Production migrations are applied by hand from `internal/` before the merge that needs them: `bunx cf d1 migrations apply <id> --dir ../workers/internal/migrations`. A deploy does not apply them.
7. `.node-version` pins Node 26.13.0, because `cf` needs Node `^22.23 || ^24.22 || ^26.12` and does not load its config under Bun.
Rationale: Louis asked on 2026-11-12 for the Workers to deploy with the `cf` CLI, not Wrangler. The sibling repos already moved on the same pins, and this repo follows them.
Evidence: `cf0.ai/docs/decisions/2026-11-06-cf-cli-and-vite-plugin.md`; `senvielab/docs/decisions/cf-cli-and-vite-plugin.md`; `elearning/docs/decisions/2026-11-09-cf-cli-and-vite-plugin.md`; `cf deploy --prebuilt --mode production --dry-run` on both builds (the site read 110 asset files with no bindings, Work showed `env.DB` and `env.ASSETS`); `cf d1 migrations list` returned `[]` after a local apply of 0001 and 0002.
Exceptions: none.
Bad example: `bunx wrangler deploy`; `cf d1 migrations apply hack-collective-work` without `--dir`; a local apply without `--local`.
Good example: `cd internal && ../node_modules/.bin/cf d1 migrations apply <id> --dir ../workers/internal/migrations --local --persist-to .cloudflare/state`.
Open decisions: none.
